# Adoption roadmap

The project should earn adoption through reproducibility and useful integration boundaries rather than growth claims.

## Stage 0 — credible repository

Required:

- one-command local demo;
- clear architecture, threat model, limitations, and vision;
- cross-platform CI;
- install and contribution guidance;
- structured issue and fixture intake;
- reproducible JSON and Markdown evidence artifacts;
- no claims broader than the tests.

## Stage 1 — independent evaluation

Required:

- independently authored fixture packs;
- clean-install receipts from outside the maintainer environment;
- benchmark versioning and review policy;
- public false-positive and false-negative reports;
- documented evaluation hardware and timing limitations;
- external review of receipt privacy and hash-chain semantics.

## Stage 2 — real runtime examples

Required:

- minimal OpenAI, Anthropic, Google, and local-runtime examples;
- explicit documentation of how each host authenticates context;
- no provider endorsement claims;
- integration tests using mocks or provider test environments;
- replay and request-correlation design;
- conformance checks shared across adapters.

## Stage 3 — portable verification

Required:

- stable request and receipt specifications;
- signed external checkpoints;
- proof of final-ledger truncation detection;
- cross-language verification implementation;
- fixture and receipt compatibility vectors;
- schema migration and revocation policy.

## Stage 4 — production pilots

Required:

- narrow pilots around repository mutation, deployment, communications, or another high-value action;
- scoped credentials and real isolation owned by the host;
- human approval for high-risk actions;
- retention, deletion, and incident procedures;
- measured integration latency;
- public postmortems or anonymized evidence when approved.

## Stage 5 — ecosystem

Potential outcomes:

- framework-maintained adapter packages;
- third-party fixture packs;
- independent receipt verifiers;
- policy libraries;
- hosted checkpoint and evidence services;
- organizational requirements for agent authority receipts.

## Discovery and community work

Healthy discovery comes from:

- a demo people can run in under a minute;
- precise diagrams and examples;
- thoughtful issue labels such as `good first issue`, `help wanted`, and `evaluation`;
- public benchmark artifacts;
- honest comparisons and limitations;
- useful integrations contributed by real users;
- release notes that explain evidence, not hype.

Stars and social attention are lagging signals. Independent receipts, outside fixtures, repeat contributors, and compatible implementations are stronger leading signals.
